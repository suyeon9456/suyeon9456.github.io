## SEO 최적화
{: .sub_title}

#### CSR 환경에서 동적 OG 태그 적용
프로젝트 랜딩 페이지를 개편하면서 각 서브 페이지에 동적인 OG 태그를 적용해야 하는 요구 사항이 있었습니다. 그러나 해당 프로젝트는 CSR(클라이언트 사이드 렌더링)을 기반으로 하고 있어 index.html에 설정된 meta 태그가 모든 페이지에 동일하게 적용되는 문제가 있었습니다. 이로 인해 SNS 공유 시 메타 태그가 적절히 반영되지 않는 문제가 발생했습니다.

CSR 환경에서 meta 태그를 동적으로 관리하기 위해 React-Helmet과 SSR처럼 HTML을 미리 렌더링해주는 React-Snap을 테스트했으나, Angular 기반에 React가 부분적으로 렌더링되는 프로젝트 구조상 적용이 어려웠습니다. 이로 인해 클라이언트가 아닌 서버 측에서 OG 태그를 동적으로 관리하는 방법을 모색하게 되었습니다. 그 과정에서 AWS의 CloudFront Function을 활용해 특정 URL 경로에 맞는 HTML을 반환하는 방식을 실험하며 동적 OG 태그 적용 가능성을 확인했습니다. AWS의 또 다른 솔루션인 Lambda@Edge와도 비교 테스트를 진행했으나, CloudFront Function이 약 1/6의 비용으로 비용 효율성이 높고 구현이 간단한 장점이 있어 최종적으로 선택했습니다.

CloudFront Function은 URL 요청을 트리거로 동작하도록 설정했으며, 요청의 User-Agent가 크롤러(봇)일 경우 URL 경로에 맞는 OG 태그가 포함된 HTML을 반환하고, 일반 사용자일 경우 원본 서버(S3) 또는 캐시된 응답을 반환하도록 구성했습니다. 이를 통해 크롤러는 OG 태그가 포함된 정적 HTML을 수집할 수 있고, 일반 사용자는 CSR로 동작하는 React 페이지를 제공받아 SEO 및 SNS 공유 최적화 문제를 효과적으로 해결했습니다.

작업 당시에는 시간이 촉박하여 다양한 대안을 충분히 검토하지 못한 점이 아쉬웠습니다. 만약 다시 비슷한 상황에 직면한다면, Angular 에서 SSR을 지원하는 @angular/platform-server나 Angular Universal등을 시도해 볼 수 있을 것 같습니다.


#### 동적 서브도메인의 검색엔진 최적화를 위한 사이트맵 관리와 개선
동적 서브도메인을 지원하는 프로젝트에서 사용자들로부터 검색엔진 노출이 원활하지 않다는 불만이 종종 접수되었습니다. 문제를 분석한 결과, 서브도메인 페이지들이 검색엔진에 제대로 색인되지 않는 원인은 사이트맵 처리 방식에 있었습니다.

기존에는 각 페이지별 사이트맵에 접근하려면 도메인 루트에서 직접 접근할 수 없었고, 서브도메인을 소유한 메인 도메인의 사이트맵 인덱스를 통해서만 접근이 가능했습니다. 또한, 각 페이지에서 생성되는 뉴스레터 URL이 동적으로 사이트맵에 추가되지 않아 최신 상태를 유지하지 못하는 문제도 있었습니다. 이를 해결하기 위해 Next.js의 서버사이드 렌더링과 Dynamic Routes 활용하여 각 서브도메인의 사이트맵과 robots.txt를 동적으로 생성하고 관리하는 방식을 도입했습니다.

사이트맵 생성 문제를 해결한 후, 이를 Google Search Console에 교차 제출(cross-submission)을 활용한 사이트맵 인덱스 방식을 유지하여 제출하였습니다. 이 과정에서 Google이 권장하는 사이트맵 크기 제한(50,000개 이하의 URL)을 준수하기 위해 여러 개의 인덱스 파일을 생성하여 관리했습니다. 

그러나 사이트맵 인덱스를 제출한 후 즉각적인 결과를 확인하기는 어려웠습니다. 크롤러가 사이트맵을 수집하는 순서와 속도가 일정하지 않을 가능성을 염두에 두고, 주기적으로 Google Search Console 데이터를 모니터링하며 크롤링 및 색인 상태를 확인했습니다. 개선 작업을 진행한 지 3개월 후, 노출 수가 약 46% 증가한 것을 확인할 수 있었습니다.

## 개발경험 개선
{: .sub_title}
#### Sentry 도입
과거에는 예기치 못한 오류가 발생할 경우, AWS CloudWatch를 통해 API 요청 및 응답 상태를 확인하거나, 개발자 도구 콘솔에서 표시되는 오류 메시지를 기반으로 문제를 분석해야 했습니다. 이 과정에서 사용자에게 콘솔 오류 메시지의 스크린샷을 요청하거나, 원격 연결을 통해 원인을 파악해야 하는 불편함이 있었습니다. 이러한 방식은 오류 상황을 신속히 확인하기 어렵게 만들었으며, 문제 해결이 지연되는 동안 동일한 오류를 겪는 사용자가 증가하는 문제로 이어졌습니다.

이러한 문제를 해결하고 오류를 체계적으로 추적 및 관리하기 위해 Sentry를 도입하게 되었습니다. 클라우드 기반 Sentry를 사용할 수도 있었지만, 비용 절감 및 데이터 보안을 위해 온프레미스(On-Premise) 방식으로 구축하였습니다. 이를 통해 데이터가 외부로 유출되지 않도록 보호하고, 내부 네트워크에서만 접근할 수 있도록 설정했습니다.

또한, beforeSend 기능을 활용하여 긴급도나 중요도가 높은 오류 로그만 필터링해 Sentry로 전송하고, 샘플링을 적용해 트래픽을 효율적으로 관리할 수 있도록 했습니다. 더불어, 운영 환경에서 발생하는 오류를 신속히 분석할 수 있도록 소스맵(Source Map)을 제공하여 개발자 경험(DX)을 개선했으며, 오류 발생 시 슬랙(Slack) 알림 시스템을 통해 실시간으로 대응할 수 있도록 설정했습니다. 이를 통해 오류 모니터링과 디버깅 프로세스가 대폭 개선되었으며, 문제 해결 속도를 높여 사용자 경험을 향상시킬 수 있었습니다.

#### 디자인 토큰 도입
디자이너와 프론트는 약속된 varient와 컬러를 사용해 협업하고 있었습니다. 그러나 팀 규모가 커지고 스프린트를 진행하면서 추가되는 컬러나 varient에 대한 프론트 팀과 디자이너 팀 간의 명명 차이가 발생했고 코드 수정 없이 디자이너가 컬러를 직접 변경할 수 없는 등 문제가 발생하기 시작했습니다.

이러한 문제를 해결하기 위해 design token을 도입하게 되었고, 이를 테스트하기 위해 github에 디자이너팀이 사용할 수 있는 브랜치를 생성하였습니다. 피그마에서 디자이너가 디자인 설정을 변경하면 그것에 대한 변경된 토큰이 피그마 플러그인을 통해 repository에 생성한 브랜치로 push 할 수 있도록 하였습니다. 토큰(.json) 파일은 코드 내에서 바로 사용할 수 없어, token-transformer와 style-dictionary로 json, ts, scss, css 등 코드에서 사용할 수 있는 파일로 변환했습니다.

그러나 이 과정을 수동으로 하게 된다면 여전히 불편함은 존재했습니다. 이를 자동화하기 위해 github actions을 사용했습니다. 변경된 토큰이 push 되면 github actions을 실행해 token-transformer와 style-dictionary 를 순차적으로 실행하여 변환한 파일을 생성하고, 생성된 파일들은 자동으로 commit 및 push 하여 개발 브랜치로 Pull Request를 생성할 수 있도록 스크립트를 작성했습니다. 이를 통해 디자이너와 프론트와의 협업이 더 원할하게 이루어질 수 있도록 개선되었습니다.

## 기술 스택 전환 및 업그레이드
{: .sub_title}
#### Next.js 버전 업그레이드 주도 
뉴스레터 아카이빙 프로젝트는 Next.js 12 버전으로 안정적으로 서비스되고 있었지만, 최신 기술 도입과 장기적인 유지보수를 위해 Next.js 14 버전으로 업그레이드가 필요하다고 판단했습니다. 최신 버전은 서버 컴포넌트, App Router, React 18 호환 등 여러 향상된 기능을 제공하여 사용자 경험(UX)과 개발자 경험(DX)을 동시에 개선할 수 있습니다. 이를 팀에 제안한 뒤, 프로젝트 업그레이드 계획을 수립하고 개발을 주도했습니다. (React 18 업그레이드 과정에서 발생한 모노레포 환경의 다중 React 버전 문제와 해결 방법은 블로그를 통해 확인하실 수 있습니다.)

App Router로의 전환은 프로젝트의 핵심적인 개선 사항 중 하나였습니다. 이 과정에서 layout을 활용하여 변동이 적은 데이터를 처리하도록 설계함으로써 코드 중복과 API 호출 횟수를 줄일 수 있었습니다. 또한, 상호작용이 필요한 컴포넌트를 제외한 나머지 부분을 서버 컴포넌트로 생성하여 클라이언트로 전송되는 JavaScript의 양을 최소화했습니다. 결과적으로 클라이언트는 필요한 HTML만 수신하게 되어 초기 로딩 속도가 더욱 빨라졌으며, SEO 측면에서도 유리한 구조를 확보할 수 있었습니다. 메타데이터 관리 방식에도 개선을 도입하여 기존의 next/head 대신 Metadata API를 활용했습니다. 이를 통해 각 페이지의 메타데이터를 선언적으로 관리할 수 있게 되었습니다.

Next.js의 빌트인 컴포넌트를 활용하여 웹 접근성 강화하였고 추가적으로 웹 접근성 강화를 위해 기존 UI에서 사용되던 태그를 시멘틱 태그로 대체 하였습니다. 이와 함께 eslint-plugin-jsx-a11y 플러그인을 ESLint 설정에 추가하여 jsx 요소에 접근성이 깨지는 부분을 개발단계에서 확인하고 수정할 수 있도록 하였습니다. 또한, 상태 관리 라이브러리를 기존 Redux에서 zustand로 전환하여 불필요한 보일러플레이트 코드를 크게 줄였습니다. 이를 통해 코드의 가독성과 유지보수성을 동시에 개선하였습니다.

QA 서버 배포 시스템에서도 변화를 주었습니다. 운영 환경에서는 Docker를 이용해 빌드한 이미지를 AWS ECR에 버전 명을 포함한 이름으로 업로드하고, 이를 AWS ECS를 통해 배포하고 있었습니다. 반면, QA 환경에서는 EC2 인스턴스에서 pm2를 이용해 애플리케이션을 실행하는 방식으로 배포를 진행했습니다. 이로 인해 QA 환경에서 배포과정에서는 발견되지 않았던 문제가 운영 환경에서 배포 시 종종 발생했습니다. 이러한 문제를 해결하기 위해 QA 환경의 배포 방식을 운영 환경과 동일하게 변경하였습니다. 이로써 환경 간 불일치를 해소하고 배포 과정에서 발생할 수 있는 잠재적인 문제를 사전에 방지할 수 있었으며, 보다 안정적이고 신뢰할 수 있는 배포 파이프라인을 구축했습니다.

Next.js 14 업그레이드는 단순히 최신 기술 도입에 그치지 않고, 프로젝트 전반의 유지보수성, 개발 생산성을 동시에 개선하는 계기가 되었습니다. 특히 페이지 로드 속도의 개선, API 호출 최적화, 상태 관리 간소화를 통해 프로젝트의 장기적인 안정성과 확장성을 확보할 수 있었습니다. 앞으로도 최신 기술을 적극적으로 도입하며 사용자 경험과 개발자 경험을 지속적으로 향상시킬 계획입니다.

## ETC
{: .sub_title}
#### 결제 데이터 문서화
입사 초기, 주요 업무는 연간 결제도 카드 결제가 가능하도록 변경하는 작업이었습니다. 가장 큰 어려움은 결제 데이터 관련 문서가 없어, 서버에서 전달되는 원시 데이터를 이해하기 위해 매번 백엔드 개발자에게 문의해야 했던 점입니다.

이 문제를 해결하기 위해 결제 데이터를 분석하고 문서화하여 프론트엔드 팀과 공유했습니다. 작성된 문서는 이후 결제 시스템 개편에서 유용하게 활용되었고, 현재는 다른 팀원이 유지·보수하며 문서화 작업에 기여하고 있습니다.

비슷한 상황에서 다시 작업하게 된다면, 데이터 처리를 효율화하기 위해 BFF(Backend-for-Frontend) 등의 방식을 도입하는 것을 검토할 것 같습니다.

#### 정산 프로세스 자동화 기능 기획 및 개발
유료 뉴스레터를 운영하는 사용자들에게 정산서를 자동으로 발송할 수 있는 기능을 기획부터 디자인, 개발까지 전담하여 진행했습니다. 우선, 백오피스의 주요 사용자인 운영팀과의 논의를 통해 요구사항을 상세히 분석한 뒤, 업무 흐름을 시각적으로 정리하고 이를 기반으로 피그마를 활용해 UI를 설계했습니다. 설계된 UI는 운영팀과 공유하며 피드백을 적극적으로 반영했으며, 백엔드 개발자와 협력해 필요한 API를 정의하고 구현했습니다.

이 프로젝트를 통해 정산 프로세스를 자동화하여 기존 작업 소요 시간을 1/3로 단축하며 운영팀의 업무 효율성을 크게 향상시켰습니다. 기획부터 개발까지 모든 단계를 사용자와 긴밀히 협업한 결과, 사용자 요구에 부합하는 완성도 높은 기능을 제공할 수 있었습니다.

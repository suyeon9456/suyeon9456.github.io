### 들어가기 🚪
팀의 규모가 커지게되면 프로덕트를 만들때 더 많고 다양한 인원이 참여하게됩니다. 기존에는 암묵적인 기준만으로도 일관된 작업을 유지할 수 있었지만, 팀원이 늘어나고 역할이 세분화되면서 더 이상 이러한 방식으로는 작업의 일관성을 유지하기 어려워 집니다. 제가 몸 담았던 팀도 비슷한 상황을 겪었죠. 디자이너와 프론트엔드 개발자는 약속된 varient와 컬러를 사용해 협업해 사용하고 있었지만 점차 컬러나 varient에 대한 프론트엔드와 디자이너 간의 명명 차이가 발생했고 디자인 요소가 추가되거나 수정이되면 정의된 값을 보며 코드를 일일이 수정해야하는 일이 잦아 졌습니다.

이러한 문제를 해결하기 위해, 디자인 시스템의 도입이 절실했고 팀내에서 간단하게 테스트 해볼 수 있는 개념을 고민하다가 디자인 토큰 도입을 테스트 해보기로 하였다. 물론 디자인이 자주 변경되지 않는 제품의 경우 

### 디자인 토큰을 적용하기 전에, 개념 알아보기 🧐
#### 디자인 시스템
제품, 서비스, 혹은 브랜드 전반에 걸쳐 일관된 디자인과 사용자 경험을 보장하기 위해 정의된 디자인 원칙, 패턴, 컴포넌트, 도구들의 체계적인 집합입니다. 

프로덕트 개발에는 디자인, 기획자, 개발자 등 다양한 팀원들이 참여하는데요, 팀 간 소통하는 과정에서 UI가 일관되지 않을 가능성이 높아집니다. 디자인이 통일성을 잃게되면 사용자는 혼란을 느낄 수 있으며, 사용자 경험을 저하시킬 수 있습니다. 즉, 디자인 시스템은 이러한 문제를 방지하고 팀 간 협업을 원할이 하기 위한 공통된 기준을 제공합니다. 또한 UI 디자인에 대한 정의와 반복 가능한 패턴을 제시하여 프로덕트를 더욱 효율적으로 개발할 수 있도록 돕습니다.

#### 디자인 토큰
디자인 토큰(Design Tokens)은 디자인 요소를 체계적이고 일관되게 관리하기 위한 재사용 가능한 작은 디자인 요소로, 디자인 시스템의 기본 구성 요소입니다. 자주 사용하는 색상, 폰트, 간격 등, 디자인 속성을 의미를 가진 이름으로 정의합니다.

디자인 토큰을 사용하면 스타일 요소들을 한 곳에서 관리할 수 있으며, 디자인의 변경이 있을때 스타일 업데이트를 자동으로 적용할 수 있습니다. 또한 동일한 토큰을 참조함으로써 디자이너와 개발자가 동일한 언어를 사용해, 혼동을 줄일 수 있습니다.

#### 디자인 토큰의 종류
토큰은 Primitive Tokens, Semantic Tokens, Component-Specific Tokens 세가지로 분류되는데, 이 각각의 개념들은 계층을 가지고 있습니다. 
* Primitive Tokens (원시 토큰)
    * 가장 기본적인 토큰이며, 원초적인 값(ex: #FFFFFF, 16px 등…)을 정의합니다.
    * 예시
        * { "color-blue-500": "#007BFF", "font-size-16": "16px", "spacing-8": "8px" }
* Semantic Tokens (의미론적 토큰)
    * Primitive Token을 기반으로 디자인 속성에 의미를 부여한 토큰입니다. (Primitive Token을 추상화)
    * 예시
        * {
        *   "primary-color": "{color-blue-500}",
        *   "text-primary": "{color-gray-900}"
        * }
* Component-Specific Tokens (컴포넌트 전용 토큰)
    * 특정 컴포넌트에 국한된 디자인 토큰이며, Primitive 또는 Semantic Tokens를 기반으로 개별 컴포넌트에서 사용하는 속성을 정의합니다.
    * 예시
        * { "button-primary-background": "{primary-color}", "button-primary-font-size": "{font-size-16}", "card-border-radius": "{spacing-8}" }


### 단순히 컬러와 변수를 적용하는 것이라면 문서화만 해도 괜찮지 않을까?
가장 큰 이유는 일관성과 생산성 때문이었습니다. 앞서 언급한 것처럼, 암묵적인 기준만으로는 디자이너와 개발자간의 명명 규칙의 차이, 수동적인 코드 수정 등이 빈번하게 발생하게 됩니다. 이는 비효율적일 뿐 아니라 오류의 가능성을 증가시키며, 일관성이 없어짐에 따라 프로덕트의 품질과 사용자 경험에도 부정적인 영향을 미칠 수 있다고 생각했습니다. 


### 테스트 과정
디자인 토큰 파일을 github repository에 반영하기
* 디자인 토큰을 활용할 수 있도로 도와주는 플러그인을 피그마에 설치합니다.
    * 다른 다양한 플러그인이 존재하겠지만 저는 Tokens Studio for Figma을 사용했습니다.
    * https://www.figma.com/community/plugin/843461159747178978/tokens-studio-for-figma
* 플러그인을 열고 새로운 디자인 토큰을 정의하거나 기존 토큰을 불러옵니다.
* 플러그인에서 내보낸 JSON 파일을 받아오기 위해 플러그인과 github를 연결해 토큰을 받아올 수 있도록 github에서 토큰을 발급 합니다.
* 디자인 토큰 파일의 변경 사항을 반영할 브랜치를 생성합니다.
* 이제 디자이너가 토큰을 변경하면 JSON 파일이 해당 브랜치로 push 됩니다.
Design Token 변환 프로세스
* 생성된 JSON 형식의 Design Token 파일은 코드에서 바로 사용할 수 없으므로, 이를 코드에서 활용 가능한 형태로 변환해야 했습니다.
* 사용 도구
    * Token Transformer: Design Token 파일을 가공하여 변환.
    * Style Dictionary: 다양한 포맷(JSON, TS, SCSS, CSS 등)으로 변환.


여기까지 진행했을 때도 여전히 불편함은 존재했습니다.
GitHub Actions를 활용한 자동화 구축
* 자동화 트리거
    * 디자이너가 Design Token을 GitHub 브랜치에 Push하면 GitHub Actions가 자동으로 실행됩니다.
        * github actions 워크플로우 파일을 생성합니다.
        *  .github/workflows 폴더에 {파일이름}.yml 파일을 생성
        * 
* Token Transformer 실행JSON 파일을 가공하여 변환.
* Style Dictionary 실행변환된 Token을 다양한 포맷(JSON, TS, SCSS, CSS 등)으로 생성.
* 파일 커밋 및 푸시변환된 파일들을 자동으로 커밋하고, 개발 브랜치로 Pull Request를 생성
